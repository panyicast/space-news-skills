# 工具协同流程：space-news + Tavily + github-deep-research

本文件用于说明 `space-news` 在实际运行中，如何与 `Tavily`、`github-deep-research`、`web_fetch`、`browser`、`gh` 等能力协同工作。

## 一、总体原则

- `space-news` 是主技能，负责整体工作流：检索、筛选、分类、排序、成稿。
- `Tavily` 是默认发现层，用于扩展搜索面、发现候选线索。
- `github-deep-research` 是辅助分析层，用于深挖高价值 GitHub / 开源项目。
- `web_fetch` 与 `browser` 是原文读取层，用于回读原始页面。
- `gh` 是 GitHub 原生数据层，用于获取仓库、Issue、PR、commit、release 等结构化证据。

## 二、默认工作流

### 第 1 步：定义任务范围

先明确：
- 时间范围
- 输出形态（周报 / 月报 / 专题研究）
- 是否有特定主题（如遥感基础模型、月球探测、开源项目）

如果时间范围超过一周，默认切片：
- 周报：通常不用切片
- 月报：按上旬 / 中旬 / 下旬或按周切片
- 多月专题：按月切片，再按主题补检

### 第 2 步：Tavily 发现层

默认使用 `Tavily` 做第一轮候选发现。

用途：
- 发现新闻、任务动态、机构公告、论文线索、项目页、媒体报道
- 扩大搜索范围，避免只盯某一类来源
- 按主题分簇跑多轮 query

注意：
- `Tavily` 只能作为发现层
- 不能直接把 Tavily 返回内容当最终事实依据
- 必须尽量回到原始页面验证

### 第 3 步：原始来源回读

对高价值候选，优先回读：
- 官方机构页面
- 论文页 / arXiv 页
- GitHub 仓库 / release / docs 页
- 项目官网
- 可信媒体原文

优先工具：
- `web_fetch`：结构简单、可读性好时优先
- `browser`：`web_fetch` 抓不干净或页面复杂时补上

### 第 4 步：GitHub / 开源项目专项深挖

当候选中出现高价值 GitHub 仓库或开源项目时，可调用 `github-deep-research`。

适用场景：
- 仓库活跃度高、增速快、战略价值明显
- 项目方向重要，但仅凭 README 难以判断
- 需要看 commit / issue / PR / release 节奏
- 需要补充竞品关系、维护状态、开发趋势

默认优先链路：
1. `gh`
2. `github-deep-research` 的 `gh` 优先脚本
3. `web_fetch` 补充仓库页 / 项目站点
4. 必要时回看 linked docs / papers / releases

注意：
- `github-deep-research` 只能做分析补充
- 不能单独构成最终来源链
- 最终仍要链接回仓库、release、docs、论文页、项目主页等原始页面

### 第 5 步：交叉验证与去重

在进入成稿前，至少完成以下检查：
- 是否多个候选实际指向同一事件
- 标题、摘要、来源链接是否一致指向同一事实
- GitHub 分析结论是否能回溯到仓库证据
- 媒体报道是否能回到官方或项目原始页面
- Tavily 发现的线索是否已被原始来源确认

### 第 6 步：space-news 成稿

最终由 `space-news` 负责输出固定格式：
- 标题
- 时间范围
- 本期摘要
- 重点事件

每条事件写作要求：
- `内容摘要` 基于原始事实提炼
- `关注点 / 影响` 只写有实质内容的判断
- 不能把 `Tavily` 或 `github-deep-research` 的中间分析直接原样塞进正文

## 三、三者分工边界

### `space-news`
负责：
- 主工作流调度
- 候选合并与筛选
- 分类、排序、成稿

不负责：
- 单独承担所有搜索
- 单独替代 GitHub 深挖

### `Tavily`
负责：
- 大范围发现候选
- 发现新闻、文章、项目、论文、媒体线索

不负责：
- 成为唯一来源
- 直接替代原始页面验证

### `github-deep-research`
负责：
- 深挖高价值开源项目
- 分析仓库结构、活跃度、Issue / PR / commit / release 证据
- 补充项目演化、维护状态、竞品关系

不负责：
- 代替全局搜索
- 单独构成最终证据链

## 四、禁止事项

以下做法默认不允许：

- 只用 `Tavily` 写完整简报
- 只用 `github-deep-research` 写完整简报
- 把搜索结果页直接当最终来源
- 把 GitHub README 当成唯一依据就下结论
- 不回查原始页面就写“影响”或“趋势判断”

## 五、推荐最小可用组合

如果环境受限，推荐最小可用链路：

- `Tavily`：发现候选
- `web_fetch`：回读原始来源
- `gh`：查看 GitHub 结构化数据
- `space-news`：成稿

如果需要更强的开源项目分析，再加：
- `github-deep-research`

## 六、推荐增强组合

在条件允许时，推荐完整链路：

- `Tavily`：发现层
- `web_fetch`：正文读取层
- `browser`：复杂页面补抓层
- `gh`：GitHub 原生证据层
- `github-deep-research`：开源深挖层
- `space-news`：筛选、排序、成稿层

这套链路的目标不是“多工具堆叠”，而是：
- 让发现更广
- 让证据更强
- 让分析更深
- 让最终简报仍然保持来源清晰、结构稳定、可验证
